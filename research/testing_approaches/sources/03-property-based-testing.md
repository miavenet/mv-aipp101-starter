## Key takeaways for this project

- The best empirical account of *which kinds of properties find which bugs* (Hughes, "How to Specify It!") found that **model-based/reference-implementation properties found every planted bug, and found them far faster** than postconditions or metamorphic properties (mean 5.8 tests to failure vs. 56–77) — this is a direct, mechanistic endorsement of the project's "naive std::map reference book compared after every event" design [S1].
- Industrial practitioner evidence agrees: in 30 interviews with experienced PBT users at Jane Street, **differential/model-based properties were the single most common high-leverage idiom (17/30 participants)**, ahead of round-trip properties (11/30) and classical mathematical properties (11/30) [S3]. Round-trip (encode/decode inverse) properties are exactly the pattern needed for the Pillar binary decoder.
- The same study is candid about PBT's costs: participants called hand-writing generators "the biggest annoyance with trying to use QuickCheck" (P6) and "tedious"/"high-effort"; one said "I hate writing shrinkers" (P4) — directly relevant to budgeting agent/reviewer time for generator and shrinker design, not just property design [S3].
- A generator that can't reach a precondition-satisfying or "interesting" state produces false confidence — demonstrated concretely by Hughes et al.'s AUTOSAR CAN-stack case study, where RANDOOP-style (non-stateful) random testing "performs very poorly, only finding the simplest bug" because reaching an operational stack state requires "around ten API calls" that naive random testing essentially never sequences correctly, while state-machine-aware generators handled it easily [S2]. This is the exact "generators that rarely hit interesting states" trap named in the brief, with a concrete empirical illustration.
- Industrial-scale evidence that PBT finds real, spec-level bugs in protocol/standard implementations: Volvo's QuickCheck-based AUTOSAR testing project modeled "over 3000 pages of textual specifications," and (per Hughes's own conference talk) found "100+ issues identified... 30+ bugs identified in the standard itself," working against vendor implementations with **no pre-existing test suite** — structurally analogous to this project's spec-only NYSE Pillar decoder work [S2][S4].
- Real production-system bug-finding via model-based PBT is also documented for Dropbox: Hughes, Pierce, Arts & Norell modeled Dropbox's synchronization semantics and found rare, real conflict-handling bugs that "the synchronization team has reproduced" and confirmed as genuine, occurring "under very special circumstances" [S5] — evidence that PBT surfaces exactly the rare-interleaving bugs unit tests miss, which matters for the A/B arbitration and gap-detection logic in this project.
- RapidCheck's own documentation describes exactly the Command/Model/Sut stateful-testing pattern the project needs for the order book, and contains a sharp correctness warning: "you need to always assert all preconditions for your command in checkPreconditions," because during shrinking RapidCheck regenerates commands only by checking preconditions against a hypothesized state, not by re-running the model — get this wrong and shrinking can silently produce invalid/misleading command sequences [S6].
- Tooling maintenance status, checked directly against GitHub (2026-09-19): **RapidCheck** (emil-e/rapidcheck) is not archived, was last pushed 2026-08-06, has 1111 stars but 120 open issues and zero formal GitHub releases — actively but thinly maintained, consistent with a small-maintainer hobby-grade project rather than a corporately backed one. **Google FuzzTest** is much more active (pushed the same day this research was done, 1052 stars, 172 open issues) and explicitly designed to unify PBT-style domains with coverage-guided fuzzing in C++. **autocheck** (thejohnfreeman/autocheck) was last pushed mid-2024 (over two years stale). **CppQuickCheck** (grogers0) was last pushed in 2016 and is effectively dead.
- On the fuzzing relationship: libFuzzer is coverage-guided and explicitly meant to run with sanitizers ("clang -g -O1 -fsanitize=fuzzer,address") and supports "Structure-Aware Fuzzing" via custom mutators for structured/binary formats — the natural pairing for a decoder is property/round-trip tests (RapidCheck) for logical correctness plus a libFuzzer or FuzzTest harness under ASan/UBSan for memory-safety/crash-class bugs on the same decoder entry point [S7][S8].
- MacIver (Hypothesis) is quoted inside Hughes's own paper making the foundational point that PBT has no crisp definition beyond convention: "Historically the definition of property-based testing has been 'The thing that QuickCheck does'" [S1] — useful context that "property-based testing" is a family of techniques (classical/invariant, postcondition, metamorphic, model-based, stateful) rather than one fixed method, which is why the project should pick model-based/round-trip properties deliberately rather than treat "PBT" as a single undifferentiated practice.

## Sources

### [S1] How to Specify It!: A Guide to Writing Properties of Pure Functions
- **Author/Org:** John Hughes (Chalmers University of Technology and Quviq AB)
- **Year:** 2020 (Lecture Notes in Computer Science 12053: 58–83)
- **URL:** https://research.chalmers.se/publication/517894/file/517894_Fulltext.pdf
- **What it measured:** A controlled comparison of five kinds of properties (invariants/validity, postconditions, metamorphic properties/preservation-of-equivalence, inductive properties, and model-based properties) against eight deliberately-planted buggy variants of a binary search tree implementation, measuring both which bugs each property type catches and how many random test executions (mean) are needed to trigger a failure.
- **Key findings (verified against raw PDF text via pypdf extraction):** "Validity properties miss many bugs (five of eight)... In contrast, every bug is found by at least one postcondition, metamorphic property, and model-based property." On speed: mean tests-to-failure were Postcondition 77, Metamorphic 56, **Model-based 5.8** (min 3.1, max 9.8) — "model-based properties find bugs far faster than postconditions or metamorphic properties." A specific example: for the same bug, a postcondition failed after 50 tests on average vs. 8.4 for the logically-equivalent model-based property, because the model-based check validates the entire result structure rather than a single sampled key. Conclusion: "Model-based testing seemed the most effective approach overall, revealing all our bugs with a small number of properties, and generally finding bugs fast." The paper also stresses testing your own generators and shrinkers ("we saw the importance of testing both our generators and our shrinkers, to ensure that other properties are tested with valid data").
- **Strength of evidence:** Controlled comparison on a single (if carefully designed) worked example with 8 seeded bugs — not a large-N industrial study, but the clearest mechanistic account in the literature of *why* model-based/oracle properties out-perform other property styles, and it is Hughes's own tutorial synthesis of decades of QuickCheck practice.
- **Relevance:** Directly validates the project's central testing strategy (naive std::map reference book as oracle, checked after every event) as the highest-leverage property style available, and gives a concrete reason (completeness + fast, structural failure) rather than just "it's a good idea."

### [S2] Find More Bugs with QuickCheck! / AUTOSAR CAN-stack evaluation
- **Authors/Org:** John Hughes, Ulf Norell, Nicholas Smallbone (Chalmers University), Thomas Arts (Quviq AB)
- **Year:** (conference paper, AST workshop-style venue; exact venue/year not independently confirmed beyond the PDF itself)
- **URL:** https://smallbone.se/papers/more-bugs.pdf
- **What it measured:** Primarily a new method ("MoreBugs") for avoiding rediscovery of already-found bugs during long random-testing runs, evaluated against RANDOOP-style random testing and plain QuickCheck+shrinking (QC+S) on several examples, including a large industrial case: a QuickCheck state-machine model (5,000 lines of Erlang, modeling 50 API functions) of an AUTOSAR CAN network stack, tested against a ~20,000-line C implementation with 9 deliberately-enabled "bugs" of varying complexity.
- **Key findings (verified against raw PDF text via pypdf extraction):** "RANDOOP-style testing... performs very poorly, only finding the simplest bug. The likely explanation... is that getting the CAN stack into a state where it is operational and interesting things can happen is a rather delicate procedure, involving around ten API calls. The generators used by QC+S and MoreBugs are aware of this and are biased to frequently generate the proper setup sequence." Also: "even the easiest to find bug only fails in less than 1% of test cases" for the state-machine-aware methods, versus RANDOOP-style testing which, "running... for an hour[,] yields no test case longer than 40 operations with an average of 13" (vs. ~40 average, several-hundred max for the state-aware generators). The paper's introduction also states the commercial version of QuickCheck "has been used to test implementations of the basic software used in vehicles against the AUTOSAR standard, finding hundreds of bugs and problems, many of them in the standard itself."
- **Strength of evidence:** Semi-controlled comparative experiment (multiple methods, same target system, seeded bugs) plus an industry-scale target system — stronger than a toy example, though the "9 bugs" are researcher-injected rather than naturally occurring.
- **Relevance:** This is the clearest empirical demonstration available of exactly the risk named in the brief: naive/unstructured generators (or naive random testing) essentially never reach the "interesting" states needed to exercise stateful protocol logic (arbitration, gap sequences, book transitions), while stateful/sequence-aware generators (which is what RapidCheck's Command/Model machinery, S6, provides) do.

### [S4] Testing AUTOSAR software with QuickCheck (and "Certifying your car with Erlang" talk)
- **Authors/Org:** Thomas Arts, John Hughes, Ulf Norell, Hans Svensson (Quviq AB / Chalmers), for Volvo Cars
- **Year:** paper 2015 (ICSTW 2015); talk (Hughes, Erlang Factory) undated, slides accessed 2026
- **URL:** paper — https://www.researchgate.net/publication/275967145 (full text 403-blocked in this session; described via search-engine summary only, see caveat below); talk slides — https://www.erlang-factory.com/upload/presentations/582/CertifyingyourcarwithErlang.pdf (fetched and text-extracted directly)
- **What it measured:** An industrial acceptance-testing project for Volvo Cars, building QuickCheck models of AUTOSAR automotive basic-software standards and testing multiple vendors' independent implementations for interoperability/spec-conformance, with **no pre-existing test suite available** to work from ("Can we get hold of the test suite in advance? NO!!! There is no test suite.").
- **Key findings:** Per search-engine-derived summary of the paper (not independently re-verified against raw paper text in this session): "over 3000 pages of textual specifications" were translated into QuickCheck models, resulting in "over 200 issues" raised with Volvo and vendors, and the approach was reported as more efficient than a prior manual approach (a "5 to 8 times less work" figure was reported by search summaries but **not independently confirmed against raw text** — treat as unverified). From the talk slides (verified against raw extracted text): "Testing code from 6 suppliers... 100+ issues identified already... 30+ bugs identified in the standard [itself]... the code is 16x smaller!" (referring to the QuickCheck+Erlang specification vs. hand-written "standard" test cases), and a specific challenge named "the Most Probable Bug," where "the minimal failing test case [is] almost always the same" — motivating techniques (like S2's MoreBugs) to avoid endlessly rediscovering the same easy bug at the expense of finding new ones.
- **Strength of evidence:** Industrial case study reported by the tool vendor/researchers themselves — strong on "this actually found real bugs at scale in a spec-only setting," weaker as independent third-party verification (Quviq/Hughes have a commercial interest in QuickCheck's success).
- **Relevance:** The closest real-world analogue to this project's situation: a binary/wire-format standard with thick written specs, multiple implementations, and testing that must work from the spec text rather than an existing oracle test suite — precisely this project's NYSE Pillar decoder situation. The "16x smaller" test code and "most probable bug" shrinking-repetition problem are both concretely actionable warnings/benefits.

### [S3] Property-Based Testing in Practice
- **Authors/Org:** Harrison Goldstein, Joseph W. Cutler, Benjamin C. Pierce, Andrew Head (University of Pennsylvania); Daniel Dickstein (Jane Street)
- **Year:** 2024 (ICSE 2024, Lisbon)
- **URL:** https://harrisongoldste.in/papers/icse24-pbt-in-practice.pdf
- **What it measured:** 30 in-depth, semi-structured interviews with experienced PBT users at Jane Street (a financial technology company with heavy PBT use), coded qualitatively for what kinds of properties people write, how they generate data, and what they find hard.
- **Key findings (verified against raw PDF text via pypdf extraction):** Categorized property idioms by interview count (out of 30): "Classical Properties (11/30)" (mathematical/data-structure invariants), "**Round-Trip Properties (11/30)**... check that a pair of functions are inverses of one another—for example, parsing and pretty-printing or encoding and decoding functions," "Catastrophic Failure Properties (7/30)" (crash/assertion-only checks, explicitly noted to blur into fuzzing), and "**Differential Properties (17/30)**... compares the system under test to a reference implementation of the same functionality that serves as a specification; these are often also called model-based properties... Differential properties were by far the most widely implemented kind of property," summarized by one participant as: "'[PBT is] most useful when... you have a really good abstraction with a complicated implementation'" (P9). On generator pain: "P6 said that writing generators for data that satisfies property preconditions is 'the biggest annoyance with trying to use QuickCheck'"; participants called it "tedious" (6/30) and "high-effort" (7/30); one said replacing hand-tuned probability distributions with type-driven derivation felt necessary because manual distribution tuning was "'a little bit of a mental strain'" (P20). On shrinking: "one participant... deemed shrinking 'necessary' (P15)," two who built their own PBT tooling "insisted that shrinking was one of the most important features they implemented," but "participants found it difficult to use the shrinking functionality," and "one plainly stated, 'I hate writing shrinkers' (P4)."
- **Strength of evidence:** Qualitative interview study (n=30) at a single, PBT-sophisticated company — not a controlled experiment, but the most detailed empirical account available of how working engineers actually use PBT day to day, including its costs.
- **Relevance:** Directly validates two of the project's core design choices (model-based reference oracle = "differential properties," most common and highest-leverage; round-trip decode/encode properties for the wire format) while flagging the two places the project should budget real effort: generator design (especially for "valid" Pillar message/event sequences) and shrinker quality — both explicitly reported as the most frustrating parts of PBT in practice.

### [S5] Mysteries of Dropbox: Property-Based Testing of a Distributed Synchronization Service
- **Authors/Org:** John Hughes, Benjamin C. Pierce (University of Pennsylvania), Thomas Arts, Ulf Norell (Quviq AB)
- **Year:** 2016 (IEEE ICST 2016, pp. 135–145)
- **URL:** https://www.cis.upenn.edu/~bcpierce/papers/ICST-2015-mysteries.pdf (conference-talk slide deck; text extracted directly)
- **What it argues/measured:** Built a formal, testable model of a file-synchronizer's expected behavior (handling concurrent writes, conflicts, and background/asynchronous server communication as nondeterminism) and used property-based random testing to compare Dropbox's real client/server behavior against the model.
- **Key findings (verified against raw extracted slide text):** Modeled specific conflict-handling behavior (e.g., "the first value to reach the server wins; other values are moved to conflict files") and found discrepancies between observed and modeled behavior; per the slides, Dropbox's own team response was: "The synchronization team has reproduced the buggy behaviours... they're rare failures which occur under very special circumstances... they're developing fixes." The paper's own framing (per search-engine summary of the full paper, not independently re-verified) is that it "discover[ed] surprising behavior in two widely deployed synchronizers."
- **Strength of evidence:** Industrial case study / third-party black-box testing of a production system, with the vendor confirming the bugs were real — one of the stronger "PBT finds real bugs that survived to production" data points in the literature, though the "two synchronizers" claim is second-hand.
- **Relevance:** Demonstrates PBT's specific strength at finding rare, timing/interleaving-dependent bugs — directly analogous to the A/B line arbitration and gap-detection logic in this project, where rare interleavings (not single-event logic errors) are the likeliest source of real bugs.

### [S6] RapidCheck — stateful/model-based testing and doctest integration (own documentation)
- **Org:** RapidCheck (emil-e/rapidcheck on GitHub)
- **Year:** documentation, accessed 2026 (master branch); repo activity checked live via GitHub API on 2026-09-19
- **URL:** docs — https://github.com/emil-e/rapidcheck/blob/master/doc/state.md and .../doc/doctest.md ; repo — https://github.com/emil-e/rapidcheck
- **What it documents:** RapidCheck's `rc::state` stateful-testing API: a `Command<Model, Sut>` base class with `apply()` (update an abstract model) and `run()` (execute on the real system under test and assert), optional `checkPreconditions()` using `RC_PRE`; and a `rc::doctest::check()` drop-in integration that reports RapidCheck property results into doctest's own statistics.
- **Key findings/quotes:** On why a model is needed at all: "a system does not always provide enough public information to be able to know the expected behavior." Critical caveat (verified via WebFetch digest of the raw doc): "you need to always assert all preconditions for your command in checkPreconditions" — because during shrinking, RapidCheck generates and discards candidate command sequences by checking preconditions against a *hypothesized* state, not by re-running the real Command/model logic, so missing or incomplete precondition checks can make shrinking behave incorrectly or non-deterministically.
- **Strength of evidence:** Primary tool documentation — authoritative on what the library actually does/requires, not evidence of effectiveness.
- **Maintenance status (checked directly via GitHub API):** Not archived; last push 2026-08-06; 1,111 stargazers; **120 open issues**; **0 formal GitHub releases** (development happens on `master` without version tags). Recent merged PRs are small (e.g., a missing `<exception>` include fix, merged 2026-08-06). This indicates a small-team/community-maintained project that is alive but not corporately backed or aggressively triaged — worth budgeting review time for edge cases the maintainers haven't had bandwidth to fix.
- **Relevance:** This is the exact API the project's order-book model-based tests will be built on; the precondition-completeness warning is a concrete correctness risk to flag for code review (an AI agent could plausibly under-specify `checkPreconditions`, causing shrinking to silently mislead about minimal failing cases).

### [S7] LibFuzzer documentation
- **Org:** LLVM Project
- **Year:** documentation, accessed 2026
- **URL:** https://llvm.org/docs/LibFuzzer.html
- **What it documents:** LibFuzzer as "an in-process, coverage-guided, evolutionary fuzzing engine," using SanitizerCoverage instrumentation to guide mutation; supports "Structure-Aware Fuzzing" via user-supplied custom mutators for structured/binary input formats; documented recommended usage compiles the fuzz target together with a sanitizer, e.g. `clang -g -O1 -fsanitize=fuzzer,address mytarget.c`.
- **Key findings:** Per WebFetch digest — "bugs in the target library may accumulate without being detected" if sanitizers are omitted, i.e., combining coverage-guided fuzzing with ASan/UBSan is the documented, intended usage pattern, not an optional add-on.
- **Strength of evidence:** Primary tool documentation.
- **Relevance:** Confirms the project's plan to pair fuzzing/PBT with ASan+UBSan in CI matches the tool's own intended usage; and that a libFuzzer harness on the Pillar decoder's byte-parsing entry point, using structure-aware mutation, is a natural complement to (not a replacement for) RapidCheck's round-trip/model-based property tests — libFuzzer is best at crash/memory-safety classes of bugs via coverage feedback, RapidCheck-style PBT is best at logical/semantic correctness via explicit properties and models.

### [S8] FuzzTest (Google)
- **Org:** Google (google/fuzztest on GitHub)
- **Year:** README/documentation, accessed 2026; repo activity checked live via GitHub API on 2026-09-19
- **URL:** https://github.com/google/fuzztest
- **What it documents:** Describes itself as bridging "the gap between fuzzing and property-based testing" for C++: `FUZZ_TEST` macros in a GoogleTest-like style, with a "domains" system (e.g., `fuzztest::Positive<int>()`) for structured/typed input generation, combined with a coverage-guided fuzzing backend. Per WebFetch digest: "At Google, FuzzTest is widely used... It has replaced the old style of writing fuzz targets" (i.e., raw libFuzzer harnesses).
- **Strength of evidence:** Primary tool documentation plus a vendor's own internal-adoption claim (not independently audited).
- **Maintenance status (checked directly via GitHub API):** Not archived; **pushed 2026-09-19** (the same day as this research), 1,052 stargazers, 172 open issues — clearly an actively developed, corporately backed project, in contrast to RapidCheck's smaller-scale maintenance.
- **Relevance:** A live alternative/complement worth tracking for this project: it directly targets the same niche (C++, property-style domains, structured generation) RapidCheck occupies, but backed by continuous Google investment and unified with coverage-guided fuzzing — relevant if the project ever needs to fuzz the raw Pillar byte-decoder rather than only property-test already-decoded structures.

## Gaps: what the sources do not answer

- None of the fetched sources discuss property-based testing of a **binary wire-protocol decoder with two redundant live feeds requiring gap detection and arbitration** specifically — the AUTOSAR/CAN case (S2, S4) is the closest analogue (a spec-defined protocol stack with multiple vendor implementations) but is not itself a market-data/dual-feed-arbitration system.
- No source here gives a rigorous, controlled (as opposed to interview-based) comparison of PBT vs. example-based/hand-written unit tests on defect-detection rate or cost — S3 is qualitative/interview-based, and S1 is a single worked example, not a broad empirical comparison.
- Mutation testing as a way to validate the quality of a PBT suite itself (as opposed to using PBT to validate application code) was not covered by any source fetched in this file — it is mentioned only as a "future work" item in S3's own recommendations (RO in that paper), not demonstrated.
- No source quantifies an appropriate "time budget per property" in CI (a topic explicitly asked about in the brief) — none of the fetched sources give concrete guidance on runtime/iteration-count tuning for CI-embedded property tests; this remains a gap.
- Determinism/seed-reproduction practices in CI were not directly addressed by any source fetched here; RapidCheck's own docs were only checked for `state.md` and `doctest.md`, not its `configuration.md` (seed/config handling), which is a likely gap worth a follow-up look if precision on this specific point is needed later.
